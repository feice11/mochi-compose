# 设计理念

[设计规范](design-principles.md) 讲「是什么」：一条条规则和数值。[应用接入规范](application-integration.md) 讲「怎么接」：逐项清单。这一篇讲「为什么」：规则背后的几条理念。

规范不可能写到每一种情况。遇到没写到的，从这里的理念推出答案；推出来的答案和规范冲突时，以规范和它的 [优先级](design-principles.md#优先级规则冲突时听谁的) 为准，并把这个缺口补进规范。

这一篇写给两类读者：

- **开发者**：理解取舍，写出不用逐条对照也合规的代码。
- **AI**：每条理念都给出「在库里怎么做」「反例」「自检问题」，可以直接当作生成和审查代码的判据。

## 一句话

> **界面是一个可信的实物：手碰到它，它立刻、连续、有来有回地回应；内容从哪来就回哪去；所有细节由库统一承担，应用只描述业务。**

底子是 Material 3 Expressive 的配色、字阶和动效 token，交互和动态参考 iOS 26，形状用 Kyant 的 G2 连续圆角，工程习惯参考 miuix。四者冲突时怎么取舍，见下面各条。

---

## 1. 连续：界面是一个物体，不是一串截图

用户看到的不应该是「状态 A」跳到「状态 B」，而是同一个东西从 A 变成 B。

- **内容不瞬切**：文字换文字用 `MochiBlurText`，图标换图标用 `MochiMorphIcon`，出现和消失用 `MochiBlurVisibility`，数字用 `MochiCounterText`，卡片高度变化用 `mochiAnimateHeight`。
- **从哪来回哪去**：菜单从按钮里长出来、原路缩回；页面从卡片（`mochiNavSource`）长成整屏，返回时缩回卡片。
- **随时可打断**：动画只由弹簧进度决定。中途掉头、再点一次，都从当前位置和当前速度接着走，不跳回起点。
- **先排版、再动画**：新内容进组合后，先让它排版、画完、帧率回稳，再开始进场动画（库里的页面、面板、对话框、标签切换已经这样做）。排版和动画开头挤在同一帧，就是一次瞬切。
- **遮挡关系也要连续**：卡片从栏下面打开时，栏随进度淡到后面去（`mochiNavOccluder`），不会被一下盖住。

**反例**：`if (loading) Spinner() else Content()` 直接切换；改完值直接 `snapTo`；关闭时从头播一遍反向动画；数字直接改。

**自检**：这一帧和上一帧之间，有没有任何像素是「凭空出现或消失」的？

## 2. 跟手第一：手指在动时，界面一帧不差

手是用户和界面之间唯一的物理连接，跟手比任何过渡效果都重要。这是优先级的第一条。

- 拖动 1:1 跟手，松手时把手势速度交给弹簧接着走。
- 拖动中逐帧变化的读数直接显示，不加计数器动画；松手后程序改值时才用过渡。
- 滚动优先于按压：在列表里按压反馈先等一下，滚动一接手就收回（`awaitMochiPress`）。
- 越界用橡皮筋（`ProvideMochiOverscroll`、`MochiScrollDefaults.flingBehavior()`），不硬停。
- 系统关了动画，弹性效果就全关，但功能照常。

**反例**：拖动时还在播上一次的动画；为了好看让滑块拖尾；手松开后先停一下再回弹。

**自检**：手指停住时，界面是不是同一帧停住？

## 3. 几何先于感觉：先对齐，再微调

好看来自稳定的几何关系，不来自逐个调出来的数字。

- **连续圆角**：`MochiRoundedRectangle` / `MochiCapsule`，半径从 `MochiTheme.shapes` 取；不用 `RoundedCornerShape`。
- **同心**：圆角容器里贴着内边距放的圆角元素，圆角 = 外圆角 − 内边距（`MochiConcentric`）。
- **四周等距**：胶囊里的图标离左端的距离，等于离上下边的距离。
- **光学平衡在几何之内**：图标按墨迹居中，文字按行框中心对称。它只做微调，不推翻同心。
- **布局承担留白，不缩放内容**：内容放不下就自然增高，不缩字，不硬裁。

**反例**：为了让某一行看着居中，单独 `offset(y = 2.dp)`；从卡片高度反算一个 scale；写死 `RoundedCornerShape(12.dp)`。

**自检**：这个数字能不能从别的尺寸推出来？推不出来的，是不是应该成为一个 token？

## 4. 实体与克制：材质可信，装饰从简

Mochi 的材质是实体：灰底白卡片，不做玻璃，不折射，不模糊背景。光只在手指按下的地方亮。

- 颜色只从 `MochiTheme.colorScheme` 和 `MochiDefaults` 取，深浅色都要成立；组件里不写死颜色。
- 渐变只用在「纯色渐隐成透明」的地方（滚动边缘、渐变遮罩），而且用 `MochiSmoothGradient`（S 曲线）。不用渐变来装饰。
- 按压反馈是从指尖亮起的柔光加轻微形变（`mochiPressGlow`、`mochiPressDeform`），不描亮边，不出现白斑。
- 震动少而准：只在状态真的变了时才震。

**反例**：给卡片加彩色渐变「显得高级」；半透明的按钮色；每次点击都震。

**自检**：去掉这个装饰，信息少了吗？没少就去掉。

## 5. 一处实现，处处复用：细节由库承担

同一种交互在库里只有一份实现。复用它，就同时拿到它所有的细节；自己重画一份，就会丢掉一半。

- 需要菜单就用 `MochiDropdown` / `MochiContextMenu`，需要按钮就用 `MochiButton` / `MochiBarIconButton`，需要设置行就用 `MochiListSection` / `MochiListRow`。不要只抽出列表或外形自己画。
- 通用效果放在 `effect/` 模块（高光、形变、融球、内容变换、遮罩），组件和应用都从这里取。
- **一个属性只有一个动画主人**：高度、位置这类属性只由一套动画控制。外层不追赶内层的中间值，也不叠第二层平滑。
- **修在根上**：视觉问题改库里的 token 或组件，并写进规范；不在某个页面里凑数字绕过去。

**反例**：「普通按钮 + 另画一个浮层」当菜单；在演示里给某张卡片单独加 padding 修圆角问题；`animateContentSize` 套在自己会动画尺寸的内容外面。

**自检**：别处再遇到同样的需求，能不能直接复用我这次写的东西？

## 6. 效果可以降级，功能不能

不同系统版本、不同性能的设备上，手势、动画节奏和最终结果都一样；少的只是装饰（融球、阴影、HDR 光）。

- 按 API 版本降级效果，不降级功能（见 [兼容性](compatibility.md)）。
- 转场只改图层属性，不每帧重新布局；离屏层只开需要的大小，只在需要时开。
- 离屏合成放在形变外层，不能被跟随形变的内容挤出直边。
- 重的工作（网络、解码）不放在组合和测量里，等 `rememberMochiNavSettled()` 之后再做，期间用 `MochiSkeleton` 占位。

**反例**：低版本直接隐藏某个功能；每帧整屏 `saveLayer`；在 `remember {}` 里解码大图。

**自检**：在最慢的设备上，这个交互还完整吗？

## 7. 真实场景说话：给业务，不给参数

组件的价值体现在真实场景里，不在调参面板里。

- **演示页**：用真实场景（锁屏通知、控制中心、收件箱、相簿），交互能玩，只留一两个最影响手感的参数。
- **应用接入**：按业务场景选用组件，用不上的写「不适用 + 原因」，不为了凑全组件加无关功能。
- **默认值就是答案**：`XxxDefaults` 给出调好的值，应用只在业务需要时才改。

**反例**：演示页放一排「刚度 / 阻尼 / 偏移」滑块却没有真实内容；为了展示组件硬塞一个用不上的标签栏。

**自检**：不看说明文字，用户能不能从画面里认出这是什么场景？

## 8. 规范是活的：发现、修复、写下来

每次修一个问题，都要回答「以后怎么不再犯」。

- 修在库层；公开行为变了，同步更新中英文文档和示例。
- 新规则写进 [设计规范](design-principles.md)，并写明它服从哪一条优先级。
- 验证分开说：格式和编译、自动化测试、实机验收各是各的，编译通过不等于视觉或交互验证通过。

## 冲突时怎么取舍

理念之间会冲突，按 [优先级](design-principles.md#优先级规则冲突时听谁的) 取舍，大致顺序是：

**跟手和可用性 > 不出错、不穿帮 > 几何 > 光学 > 内容不瞬切 > 还原 iOS > 性能和兼容。**

例：拖动中的读数直接跳（跟手 > 不瞬切）；HDR 大面积光只轻微提亮（不过曝 > 还原 iOS）。

## 写代码时的判断顺序（给开发者和 AI）

1. **先分清任务**：是「用库开发应用」，还是「修改库」？两份清单不混用。
2. **找现成的**：库里有对应组件或效果吗？有就完整地用，不抽一半自己画。
3. **取 token**：颜色、字号、圆角、间距、动效，能从主题或 `XxxDefaults` 取的不写死。
4. **查连续性**：每一处会变的内容，选好过渡（理念 1）；每一处动画，确认可打断、从当前状态继续、只有一个主人。
5. **查跟手**：有手势的地方，拖动中是否 1:1、松手是否接上速度。
6. **查几何**：圆角是否同心，四周是否等距，内容会不会被裁。
7. **查遮挡和层级**：浮在内容上的栏是否登记了遮挡物；离屏层是否在形变外层。
8. **说清楚验证**：哪些编译过、哪些测过、哪些需要实机看，分开报告。

## 常见反模式速查

| 反模式 | 违背 | 改成 |
|---|---|---|
| `if (a) A() else B()` 直接换 | 连续 | `MochiBlurCrossfade` / `MochiBlurVisibility` |
| `Text(count.toString())` 直接改数字 | 连续 | `MochiCounterText` |
| `RoundedCornerShape(n.dp)` | 几何 | `MochiTheme.shapes.*` / `MochiRoundedRectangle` |
| 写死 `Color(0xFF…)` | 实体与克制 | `MochiTheme.colorScheme` / `MochiDefaults` |
| 装饰性渐变 | 实体与克制 | 主题容器色纯色 |
| `clickable` + 默认水波纹 | 实体与克制 | `mochiPressDeform` + `mochiPressGlow`，`indication = null` |
| 普通按钮 + 自己画的浮层 | 复用 | `MochiDropdown` / `MochiPopoverButton` |
| 通用卡片里摆裸 `Row` 当设置项 | 复用 | `MochiListSection` / `MochiListRow` |
| 外层 `animateContentSize` 包着会变尺寸的内容 | 一个主人 | 只留一套尺寸动画 |
| 在某个页面里凑 padding 修视觉问题 | 修在根上 | 改库层 token 或组件，写进规范 |
| 一出现就播动画，内容还没排好版 | 先排版再动画 | 交给库的转场，或先等帧率回稳 |
| 自己画的浮动栏没登记 | 遮挡连续 | 最外层加 `mochiNavOccluder()` |
| 一排调参滑块的演示 | 真实场景 | 真实场景 + 一两个关键参数 |

## 一个小对照

```kotlin
// ✗ 写死颜色和圆角，系统水波纹，文字瞬切
Box(
    Modifier
        .background(Color(0xFFEFEFEF), RoundedCornerShape(16.dp))
        .clickable { on = !on },
) { Text(if (on) "已开启" else "已关闭") }

// ✓ 主题颜色和连续圆角，按压形变 + 指尖高光，文字模糊替换
val shape = MochiTheme.shapes.extraLarge
Box(
    Modifier
        .mochiPressDeform()
        .background(MochiDefaults.groupedContainer(), shape)
        .mochiPressGlow(rememberMochiGlowState(), shape)
        .clickable(interactionSource = remember { MutableInteractionSource() }, indication = null) { on = !on },
) { MochiBlurText(if (on) "已开启" else "已关闭") }
```
